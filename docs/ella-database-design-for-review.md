What is using the 5.4 GB of server disk space:

The key point: the actual student data (database) is only 664 KB out of 5.4 GB used. That is 0.01% of the used disk space. The rest is the operating system, Docker, and the app code itself.

Will this keep increasing over time?

  Fixed costs (do not grow with users or time):
    Ubuntu OS and system libraries — stays at ~1 GB forever
    Docker images — stays at ~1.4 GB, only changes when we update the app
    Code repository — grows slightly with each deployment, maybe 10-20 MB per year

  Variable costs (grow with users and usage):
    Database — grows ~7.5 MB per student per year at 20 min/day usage
    Logs — grows slowly, can be rotated and cleaned automatically
    Docker build cache — grows with each new build, but can be cleaned anytime

  Summary: the 5.4 GB is mostly fixed infrastructure cost. It will not double just because users double. The only part that grows proportionally with users is the database, which is currently 664 KB and will remain small for a long time. At 10,000 active students using the app 20 minutes per day, the database would be approximately 75 GB per year — still manageable on the current server.


SECTION 1 — WHAT WE HAVE TODAY (CURRENT DATABASE STRUCTURE)

The current database has 5 tables. It supports the placement screening flow that is live in the pilot.

Users
Stores one row per student. Contains their name, age, location, English level (assigned after placement), and coaching preferences.

Placements
Stores the result of each placement screening. Contains the level assigned, the confidence of the assessment, a highlight sentence shown to the student, and the full conversation transcript.

Conversations
Stores one row per conversation session. Contains the topic, duration, whether it was completed, and when it happened.

Messages
Stores every turn in every conversation. Contains who said what (student or Zoe), any grammar correction, and timing data.

Session Analyses
Stores the post-session analysis generated by Zoe after each conversation. Contains the overall quality rating, best moment, what to try next, and per-turn notes.


SECTION 2 — THE ELLA CONVERSATION FRAMEWORK

The Ella Framework is a CEFR-aligned curriculum that defines what Zoe talks about and how she coaches students at each level. It was created separately and currently lives in a spreadsheet. It needs to move into the database so Zoe can use it.

The framework has three components per level:

I Can Statements
For each of the 6 levels (A1 to C2), there are approximately 18 to 21 statements across three categories: Vocabulary, Grammar, and Fluency. Each statement describes something the student should be able to do at that level. Example: "I can talk about the past using past simple — I went, I ate, I saw."

Topics
For each level, there are 11 to 12 conversation topics. Each topic has a title, a description, a reason why it works at that level, and 3 conversation starters. Example topic at A1: "My school — naming school subjects, describing the school day, saying what you like and don't like."

Transitions
Between each pair of adjacent levels (A1 to A2, A2 to B1, etc.) there are 5 transition steps. Each step has a name, a focus, a context paragraph, and 2 to 4 I can statements. The transitions define how a student moves from one level to the next.


SECTION 3 — PROPOSED DATABASE EXTENSION

To connect the framework to Zoe's behaviour, we need two types of new tables: static framework tables (seed data that never changes) and user progress tables (grow with usage).

Static Framework Tables (loaded once, shared across all users)

Framework Levels
6 rows, one per CEFR level. Stores the level code (A1, A2, etc.) and the headline statement for that level.

Framework Categories
18 rows. For each level, three categories: Vocabulary, Grammar, Fluency. Each stores the CEFR context paragraph that describes what students at that level can do in that category.

Framework Statements
Approximately 126 rows. One row per I can statement. Links to its category and level.

Framework Transitions
5 rows. One per level boundary (A1 to A2, A2 to B1, etc.). Stores the overview and transition context.

Framework Transition Steps
25 rows. Five steps per transition. Each step has a name, focus, and context paragraph.

Framework Transition Statements
Approximately 75 rows. The I can statements within each transition step.

Framework Topics
71 rows. One per topic across all levels. Stores title, theme, description, and why it works.

Framework Topic Starters
213 rows. Three conversation starters per topic.

Total static framework data: approximately 380 KB. This is shared across all users and never grows.

User Progress Tables (grow with usage)

User Framework Progress
One row per student. Tracks their current level, whether they are in a transition, and which transition step they are on.

User Statement Progress
One row per I can statement demonstrated by a student. Records when it was demonstrated and in which conversation. This is how mastery is tracked.

User Topic History
One row per topic a student has done. Prevents Zoe from repeating topics.


SECTION 4 — HOW IT ALL CONNECTS

The flow when a student starts a conversation:

1. Backend looks up the student's current level from User Framework Progress
2. Backend selects a topic from Framework Topics for that level, excluding topics already in User Topic History
3. Backend loads the I can statements for that level from Framework Statements
4. Backend builds Zoe's prompt with the topic, starters, and I can statements
5. During the conversation, Zoe watches for the student demonstrating I can statements
6. After each turn, the backend records demonstrated statements in User Statement Progress
7. After the session, the backend checks how many statements have been mastered
8. If enough statements are mastered across Vocabulary, Grammar, and Fluency, the student moves into the transition steps
9. After completing all 5 transition steps, the student advances to the next level


SECTION 5 — STORAGE ESTIMATES

Static framework data: 380 KB, one-time, shared across all users. This never grows regardless of how many students use the app.


HOW THE PER-STUDENT NUMBERS ARE CALCULATED

First, some baseline assumptions:
  One conversation turn = approximately 30 seconds of talking
  One turn stored in the database = approximately 500 bytes (student message + Zoe reply combined)
  One topic session = approximately 15 turns (about 7-8 minutes)
  One I can statement demonstrated per session = 1 row = 100 bytes
  One topic completed = 1 row = 100 bytes

At 20 minutes per day:
  Turns per day: 40 turns (20 minutes divided by 30 seconds per turn)
  Messages stored per day: 40 turns x 500 bytes = 20,000 bytes = 20 KB per day
  Topics completed per day: approximately 3 topics x 100 bytes = 300 bytes per day
  Statements demonstrated per day: approximately 5 x 100 bytes = 500 bytes per day
  Total per day: approximately 21 KB
  Total per year (if used every single day): 21 KB x 365 days = approximately 7.5 MB per student per year

At 3 hours per day:
  Turns per day: 360 turns (3 hours divided by 30 seconds per turn)
  Messages stored per day: 360 turns x 500 bytes = 180,000 bytes = 180 KB per day
  Topics completed per day: approximately 24 topics x 100 bytes = 2,400 bytes per day
  Statements demonstrated per day: approximately 20 x 100 bytes = 2,000 bytes per day
  Total per day: approximately 184 KB
  Total per year (if used every single day): 184 KB x 365 days = approximately 66 MB per student per year

At 6 hours per day:
  Turns per day: 720 turns (6 hours divided by 30 seconds per turn)
  Messages stored per day: 720 turns x 500 bytes = 360,000 bytes = 360 KB per day
  Topics completed per day: approximately 48 topics x 100 bytes = 4,800 bytes per day
  Statements demonstrated per day: approximately 30 x 100 bytes = 3,000 bytes per day
  Total per day: approximately 368 KB
  Total per year (if used every single day): 368 KB x 365 days = approximately 132 MB per student per year

Important note on the yearly calculation: The per-year numbers assume a student uses the app every single day at the same frequency. In reality this will not happen. Real usage patterns for a learning app look more like this:

  Week 1-2 (new user excitement): daily use, high frequency
  Month 1-3: 3-4 days per week on average
  Month 3+: 1-2 days per week for retained users, many users drop off entirely

A more realistic estimate for an active retained student is 100-150 active days per year, not 365. This means the realistic storage per retained student per year at 20 min/day is closer to 2-3 MB, not 7.5 MB.

The 365-day calculation is a planning ceiling — it tells us the maximum possible storage per student. The actual storage will be lower because no student uses any app every single day for a full year.


AT SCALE

The table below shows two scenarios. Worst case assumes every registered student uses the app every single day for the full year. Realistic assumes 15% of registered students are active on any given day, and active students use the app on average 120 days per year (not 365).

Students registered    Worst case (365 days)    Realistic (120 days, 15% DAU)
1,000                  7.5 GB per year          378 MB per year
10,000                 75 GB per year           3.8 GB per year
1,00,000               750 GB per year          38 GB per year
1,00,00,000 (1 crore)  7.5 TB per year          3.8 TB per year

The realistic numbers are 5 to 10 times lower than the worst case because no student uses any app every single day for a full year, and a significant portion of registered users become inactive over time.

The current server (AWS EC2 t3.micro, 19 GB disk) handles the pilot comfortably. For 10,000 registered students, a mid-range server with 500 GB storage is sufficient. Beyond 1 lakh students, a managed database service (AWS RDS) with automatic archiving is recommended.

The biggest storage driver is the messages table (every conversation turn). At scale, old messages should be archived to cold storage after 30 days and replaced with session summaries. This reduces storage cost by approximately 80%.


SECTION 6 — WHAT STAYS ON THE DEVICE VS THE SERVER

On the server (permanent, shared across devices):
  Student level and transition state
  I can statement mastery history
  Topic history (which topics done)
  All conversation messages and analyses
  Placement results

On the device (temporary, local only):
  Auth token (for API calls)
  Cached copy of current level and name (for offline display)
  Coaching preferences (grammar, vocabulary, fluency settings)
  Celebration animation state (shown in the moment, not stored)

If a student reinstalls the app or switches phones, all progress is preserved because everything meaningful lives on the server.


SECTION 7 — OPEN QUESTIONS FOR DISCUSSION

1. Mastery threshold: How many I can statements demonstrated = ready to transition to the next level? Suggested: at least 4 out of 7 per category (Vocabulary, Grammar, Fluency) across at least 3 different sessions.

2. Topic repetition: Should topics ever repeat? Suggested: yes, after the student has completed all topics at their level, topics reset and can be used again.

3. C1 and C2: The framework covers all 6 levels but the target audience (grades 5 to 12) will mostly be A1 to B1. Should C1 and C2 be seeded now or added later?

4. Message archiving: At what user count should we implement automatic archiving of old messages to cold storage? Suggested: at 10,000 active students.
